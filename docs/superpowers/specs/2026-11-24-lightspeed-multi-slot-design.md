# 1 つの Lightspeed レシーバーにつないだ複数台のバッテリーを読む（fork Issue #2）

## 目的

1 つの Logitech Lightspeed レシーバー（`046d:c547`）に G913 TKL（キーボード）と G502 X LIGHTSPEED（マウス）をペアリングしたとき、2 台のバッテリーをそれぞれ別のカードに出す。今はキーボードが起きている限りキーボードしか出ず、マウスは一度も読まれない（Issue #2 の調査結果を参照）。

fork（`rurute/battery-hub`）の中で、自分の環境で使えればよい。upstream には出さない。

## ゴール / 非ゴール / アンチゴール

- ゴール: 「Add device」に、レシーバーの先にある機器が 1 台ずつ（`G913 TKL`、`G502 X LS`）出る。それぞれ追加すると、別々のカード・トレイアイコン・名前・非表示・並び順・履歴を持つ。
- ゴール: スロットの番号が変わっても（ペアリングし直しなど）、同じ機器は同じカードのまま。
- 非ゴール: 既存のレシーバー単位のカードの設定（名前など）を新しいカードへ自動で引き継ぐこと。ユーザーは自分だけなので、手で追加し直す。
- 非ゴール: 有線で接続したキーボード（`046d:c343`）とレシーバーのスロット 1 を、同じ機器として 1 枚のカードにまとめること。
- 非ゴール: Issue #2 の「別に見つかったこと（仮説）」（0x8F のエラーが COL01 に届くため、battery の読み取りで `device is off` ではなく `timeout` になっているかもしれない件）を直すこと。ただし、下のスロットの列挙では同じ問題に当たるので、列挙の中では対処する。
- アンチゴール: 既存のレシーバーのカードが読めなくなること。Bolt / Unifying や、レシーバーを使わない Logitech 機器の動きが変わること。一覧を取るたびに寝ている機器を起こしたり、一覧の表示が目に見えて遅くなったりすること。

## 検討した案

1. **一覧を作るときにレシーバーを機器ごとに分ける**（採用）: worker の `enumerate` で Logitech のレシーバーにペアリング情報を問い合わせ、機器ごとに仮想の logical device を作る。Add device・カード・store・poller は今の「1 logical device = 1 カード」のまま動き、変更が catalog / hidpp にほぼ収まる。代わりに、一覧を作るたびにレシーバーとのやり取りが入る（レシーバー自身が答えるので速く、poller 側は一覧を 5 分キャッシュする）。
2. **driver の `identify` のような問い合わせで、main と poller がそれぞれ展開する**: `enumerate` は I/O なしのまま保てるが、展開する処理が main（Add device）と poller の 2 か所に要り、`attemptRead` の ID の照合も変える必要がある。手間が 1 より大きい。
3. **レシーバーは 1 枚のカードのまま、中に複数のバッテリーを出す**: UI・トレイ・通知・履歴がすべて「1 カード = 1 値」なので作り直しが大きすぎる。外した。

## 設計

### 機器の列挙（worker、`enumerate`）

`hid-worker.js` の `enumerate` は、`listLogicalDevices()` の結果をそのまま返すのではなく、hidpp driver の新しい関数（例: `expandReceivers(devices)`）を通してから返す。

- 対象: `vendorId === 0x046d`、製品名が `/receiver/i` に当たり、HID++ の短いレポートの collection（`0xFF00/0x0001`）と長いレポートの collection（`0xFF00/0x0002`）の両方を持つ logical device。Lightspeed 以外の Logitech のレシーバー（Unifying / Bolt）も同じ条件に当たりうる。同じレジスタで答えるならそのまま対象にしてよく、答えなければ子を作らずに今の動きのままにする（どちらでも害がないようにする）。
- 各スロット n = 1〜6 について、HID++ 1.0 の long register の読み取り（`0x83`）でレジスタ `0xB5`、サブアドレス `0x20 + (n-1)`（pairing info）を問い合わせる。
  - Issue #2 の実測では、送る側は短いレポート `10 ff 83 b5 <sub> 00 00`、返答は長いレポート `11 ff 83 b5 <sub> ...`。
  - 返答の params（`b5` の次から）: `[0]` サブアドレス、`[3..4]` 無線 PID（ビッグエンディアン）、`[7]` 機器の種類（`01` = キーボード、`02` = マウス、ほかの値もある）。実測例: スロット 1 `20 07 08 40 8e 11 00 01 ...`、スロット 2 `21 08 08 40 9f 11 00 02 ...`。
  - 空のスロットは `0x8F`（HID++ 1.0 エラー、短いレポート）で err `0x09` を返す。実測では、このエラーは長いレポートの collection では受け取れず、短いレポートの collection（COL01）も読む必要があった。**列挙では両方の collection を読む**（短い側に送って、両側の返答を待つ）。どちらに届いたかは記録していないので、実機で確かめる。
- ペアリング情報が取れたスロットだけ、続けてサブアドレス `0x40 + (n-1)`（device name）を問い合わせ、短い名前（実測: `G913 TKL`、`G502 X LS`）を取る。Linux / Solaar の解釈に合わせ、params `[1]` が長さ、`[2..]` が ASCII の名前。取れなければ名前は機器の種類から作る（例: `Logitech keyboard`）。
- ペアリングされた機器ごとに、子の logical device を 1 つ作る:
  - `id`: `${parent.id}:${wpid}`。`wpid` は 4 桁の小文字 16 進（例: `046d:c547:<serial>:408e`。数字の vendorId/productId は catalog と同じ表記に合わせる）。スロットの番号は ID に入れない。
  - `vendorId` / `productId` / `serialNumber` / `manufacturer` / `channels`: 親と同じ。
  - `product`: 短い名前。
  - 追加の情報: `receiver: { slot, wpid, kind }`（名前は builder に任せる）。
- 親（レシーバーそのもの）の logical device も一覧に残す。既存のレシーバーのカードが今のまま読めるようにするため。親には「子を持つ」ことがわかる印を付ける（例: `expanded: true`）。
- 子が 1 台もない（全スロットが空、または問い合わせに答えない）レシーバーは、印を付けずに今のまま返す。
- 問い合わせの失敗（タイムアウトや、collection を開けないなど）で `enumerate` 全体を失敗させない。そのレシーバーは展開しないで返す。
- 速さ: 1 回の問い合わせの待ち時間は今の `REPLY_MS`（400 ms）程度。空のスロットはエラーの返答で早く終わる想定。エラーが受け取れない環境では、空のスロット 4 つ分で 1.6 秒ほど遅くなる。`hid-client` の `enumerate` のタイムアウト（20 秒）には十分収まる。
- **展開の結果を worker の中で覚えておく**（設計者の判断）: `enumerate` は poller の 5 分のキャッシュ以外からも呼ばれる（Add device、capture、diagnostics、device report）。また poller は、カードが 1 枚でも見つからないと毎回一覧を取り直す。そのたびにレシーバーへ問い合わせないように、展開の結果（スロット・wpid・種類・名前）をレシーバーの親の `id` ごとに worker の中で覚えておく。
  - 覚えた結果を使うのは、同じ親が一覧に出ている間。親が一覧から消えたら捨てる（抜いた・挿し直した）。
  - 問い合わせ直すのは、覚えた結果がないとき、または `enumerate` に「取り直す」指示（例: `enumerate({ fresh: true })`）があったとき。poller の手動 Refresh（`pollOnce({ force: true })` の `invalidateLiveCache()` のところ）と Add device の一覧はこの指示を付ける。
  - 問い合わせ直して失敗したとき（タイムアウトなど、1 台もペアリング情報が取れないとき）は、前に覚えた結果があればそれを使い続ける。カードが一時的な失敗で「not connected」にならないようにするため。覚えた結果がなければ、展開しないで返す。
- **同じレシーバーへのやり取りを 1 つずつにする**（設計者の判断）: `hid-worker.js` はメッセージを並行で処理するので、Add device の一覧（展開の問い合わせ）と poller の `readBattery` が同じレシーバーで重なりうる。`exchange()` は最初に溜まっている返答を捨てるので、重なると片方がタイムアウトする。hidpp driver の中で、レシーバー（親の長いレポートの collection の path）ごとにやり取りを直列にする（Promise のチェーンによるロック）。展開の問い合わせと `readBattery` の両方がこのロックを通る。ほかの driver と `exchange.js` / `session.js` は変えない。

### Add device（main、`devices:list-live`）

- 子を持つ親（`expanded`）は一覧に出さない。子だけを出す。
- 子の `suggestedDriver` は `hidpp`（`detectDriver` が子にも当たる。親と同じ channels を持つので今の `matches` で当たる）。
- 既存の親のカードは一覧から消えるだけで、カードとしては残り、今と同じように読める。

### 読み取り（hidpp driver、`readBattery`）

- `readBattery(logicalDevice)` に `logicalDevice.receiver` があるときは、そのスロットだけを探す（`findRoute` でスロットの候補を `[receiver.slot]` にする）。0x1004 → 0x1000 → 0x1001 の順で探すのは今と同じ。
- `routes` のキーを `channel.path` から、子のときは `channel.path + '|' + wpid` に変える（親や直接接続の機器は今のまま `channel.path`）。これで 1 つのレシーバーで複数の読み先を覚えられる。
- スロットは、一覧を作ったときの値を使う。そのあいだにペアリングし直してスロットが変わるのはまれなので、追いかけない。手動の Refresh では展開を取り直すので、そこで直る。
- 覚えている読み先（route）にはスロットも入れておき、使う前に `receiver.slot` と同じか確かめる。違えば読み先を捨てて探し直す（設計者の判断）。こうしないと、古いスロットに別の機器が入ったとき、別の機器のバッテリーが出続ける。
- 親（`receiver` なし）の読み取りは今のまま（最初に見つかった 1 台）。

### カードと保存（poller / store / identity）

- カードの扱いは変更しない想定。子は ID が違う別の logical device として、今の仕組みでそのまま扱われる。poller と main で変えるのは、上の「取り直す」指示を `enumerate` に渡すところだけ（`hid-client.enumerate` に引数を足し、worker まで渡す）。
- `identityOf()` は `serialNumber` があればそれを見る。子は親と同じシリアル番号を持つが、Bluetooth のアドレスの形（12 桁の 16 進）でなければ identity は付かないので、親と子がマージされることはない。**実機のレシーバーのシリアル番号がこの形に当たらないか、builder が確かめる**。当たるなら、子では identity を付けない。
- 子は `hasWiredIdentity` のような兄弟の探索をしない（hidpp は持っていない）。

## テスト

既存の `test/protocols.test.js` の書き方（`node:test`、ハードウェアなし）に合わせる。

- ペアリング情報の返答から無線 PID・種類を取り出す関数と、名前の返答から名前を取り出す関数（実測のバイト列を使う）。
- 子の logical device の作り方（ID・product・`receiver`・親の印）。
- `expandReceivers` で、レシーバーに当たらない機器は手を付けないこと、空・エラーのスロットは飛ばすこと、問い合わせがすべて失敗したら今のまま返すこと（exchange を差し替えて確かめる）。
- `readBattery` で、子は自分のスロットだけを探し、`routes` が子ごとに分かれること。スロットが変わったら探し直すこと。
- 展開の結果を覚えること: 2 回目は問い合わせないこと、`fresh` で問い合わせ直すこと、問い合わせ直して失敗したら前の結果を使うこと、親が消えたら捨てること。
- 同じレシーバーへの 2 つのやり取りが重ならないこと。

実機（Windows）では、fork の手動ビルド（`build.yml`）でインストーラを作って確かめる:

- Add device に `G913 TKL` と `G502 X LS` が別々に出て、レシーバーそのものは出ない。
- 2 枚とも追加すると、それぞれのバッテリーが出る（キーボードは約 95%、マウスは 81% 前後）。
- マウスを寝かせても、キーボードのカードは読み続けられ、マウスのカードは今のスリープ時と同じ表示になる。
- 既存のレシーバーのカードが今のまま読める。

## builder に任せること

- 関数名・引数の形・子に付ける情報のフィールド名。
- 2 つの collection に書いて読む処理を `exchange.js` に足すか、hidpp の中に書くか。どちらにしても、handle は `session.js` から取る（`session.js` の先頭コメントのとおり、handle は閉じない）。
- 名前が取れなかったときの初期値の文言。
